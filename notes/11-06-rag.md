## Remember these 3 things

1. **Two halves, one contract.**
   - Offline: chunk → (optional header) → embed in one batch → normalize → store with `{doc, text}`.
   - Online: embed the query (same model, its query prefix, same normalization) → top-k → assemble → generate.
   - If you change the embedding model, chunker or header rule, **re-embed everything**. Query and doc vectors from different models aren't comparable.
   - RAG is for **knowledge** (facts that change, need citations). Fine-tuning is for **behaviour** (format, tone, style).
2. **Grade with a 2×2 table, not one accuracy number.**

   | | correct | not correct |
   |---|---|---|
   | **gold retrieved** | success | **generation_failure** (fix the prompt/model) |
   | **gold not retrieved** | **suspicious** (parametric memory or missing gold label) | **retrieval_failure** (fix chunking/embedding/query) |

   - Unanswerable questions: correct_abstain vs **hallucination**.
   - Citations are checked **mechanically**: in range 1..k, and the cited chunk contains the figure. Map `[i]` through the **shown order** (edge reorder), not the retrieval order.
3. **Chunks lose their entity. Put it back.**
   - 10-K paragraphs say "the Company". 32 filings have the same capex sentence with different numbers, so the query can't tell them apart.
   - Plain: 10/20 (8 retrieval failures, 2 generation failures). Header `[Halcyon Insurance 10-K FY2024] `: **20/20**, +16 tokens per question.
   - Wrong context makes the model *more* confident: closed-book abstained 24/24, but plain RAG stated **10 wrong $ figures, all with citations**.

## In plain English

RAG is an **open-book exam**. Before the exam, you cut the textbook into index cards and file them by topic (offline). During the exam, you look up the few cards that match the question, lay them on the desk, and answer only from them (online).

Two things can go wrong, and they need different fixes. Either you **pulled the wrong cards** (retrieval failure: fix the filing), or you **had the right card and still wrote the wrong answer** (generation failure: fix how you read). One accuracy number hides which one happened. The 2×2 table shows it.

The trap in my experiment: every card said "the Company's capital expenditures were $X". With the company name cut off, the cards from 16 companies look the same. Writing the company name at the top of each card fixed everything. Worse, when the student pulled the wrong card, they didn't say "I don't know". They copied the wrong number confidently and cited the card. With no cards at all, they honestly said "I don't know".

## Worked example

**Shown order vs retrieval order** (k = 5, edge reorder):

| Cited `[i]` | Model saw (shown) | `retrieved[i-1]` (bug) | Same? |
|---|---|---|---|
| 1 | r0 | r0 | ✓ |
| 2 | r2 | r1 | ✗ |
| 3 | r4 | r2 | ✗ |
| 4 | r3 | r3 | ✓ |
| 5 | r1 | r4 | ✗ |

Skipping the mapping makes citations to positions 2, 3 and 5 look wrong. The bug hides because most replies cite `[1]`. (My prediction said "r0 and r2"; the right answer is positions **1 and 4**.)

**My experiment** (32 fictional 10-Ks = 96 chunks at size 600; 20 answerable + 4 unanswerable; BGE-small; llama3.2 3B, T=0, num_ctx 8192):

| Condition | Answerable correct | Citation ok | Abstained (unanswerable) | Wrong $ stated | Buckets | Tokens / latency |
|---|---|---|---|---|---|---|
| closed-book | 0/20 | 0/0 | 4/4 | **0/24** | retrieval_failure 20, correct_abstain 4 | - |
| RAG plain | 10/20 | 10/10 | 4/4 | **10/24** | success 10, gen_fail 2, retr_fail 8 | 697 / 1.4 s |
| RAG header | **20/20** | 20/20 | 4/4 | 0/24 | success 20 | 713 / 1.6 s |

Generation-failure examples (plain): "Halcyon Insurance capex FY?" → `$466 million [2]`. The gold chunk *was* in the top 5, next to four other companies' capex chunks, and the model picked the wrong one. That `[2]` passes `citation_ok`, because the chunk really says $466 million. A citation shows the number came from the doc, not from the *right* doc.

My predictions: closed-book 0/20 ✓, wrong $ 20/24 ✗ (real 0/24), plain 10/20 ✓, header 20/20 ✓, retrieval failure dominates ✓.

## Formulas / cheat sheet

- `q = normalize(embed(QUERY_PREFIX + question))`, `scores = D @ q.T`, top-k. Same normalization on both sides.
- `shown_ids = reorder_edges(retrieved_ids, scores)`. Then `[i]` → `shown_ids[i-1]`.
- Whole-number match: `(?<![\d,])` + `re.escape(f"{v:,}")` + `(?![\d]|,\d)`. A comma is allowed after the number ("$1,284, up from…") only when no digit follows.
- Bucket rule: `gold_retrieved = any(g in retrieved for g in gold)`; `correct = whole_number_match and not abstain`.
- Header (contextual chunk): `f"[{title}] " + chunk`, **before** embedding, and kept in the stored text so the LLM sees it too.

## Where this shows up in AI engineering

- **Project 1 (RAG over SEC filings):** this exact pipeline. Contextual headers (company, form, fiscal year, section) on every chunk; a golden set with gold chunk ids; the 2×2 bucket report in CI; a citation check on every answer.
- **Interviews:** "Your RAG answers are wrong. How do you debug?" → split into retrieval vs generation with a gold-labeled set, then fix the half that's broken. "RAG vs fine-tuning?" → knowledge vs behaviour.
- **Production:** metadata filters (company = X, fy = 2024) do what my header did, but as a hard filter. Log retrieved ids, shown order and the reply for every call.

## Mistakes to avoid

- **Chunks without their entity:** "the Company" paragraphs from 16 companies look the same. Add a header or metadata filter.
- **Assuming RAG reduces hallucination:** wrong context *creates* confident wrong answers (0 → 10 wrong $ figures).
- **Mapping citations through retrieval order** when the prompt used edge order.
- **Trusting a valid citation as proof of correctness:** it proves support, not the right entity.
- **Substring matching numbers:** `1,284` ⊂ `11,284`. Match whole numbers.
- **One accuracy number:** 10/20 doesn't say whether to fix the retriever or the prompt.
- **Changing the embedding model without re-indexing.**

## Words

- **RAG:** retrieval-augmented generation; retrieved text is added to the prompt at query time.
- **Offline / online half:** indexing (chunk, embed, store) vs answering (embed query, retrieve, generate).
- **Gold chunk:** the chunk that actually contains the answer, labeled in the eval set.
- **Generation failure / retrieval failure / suspicious:** the 2×2 buckets above.
- **Parametric knowledge:** what the model memorized in training (as opposed to the retrieved context). My fictional corpus blocks it.
- **Contextual chunk header:** a prefix naming the source (title, section) so a chunk makes sense alone.
- **Grounding / faithfulness:** the answer is supported by the retrieved text.
